# Checkout / Orders Test Plan

## Application Overview

This plan covers the AutomationExercise "Checkout / Orders" chunk: `/view_cart` -> "Proceed To Checkout" -> the login-gate (`#checkoutModal` when logged out; straight-through when logged in) -> `/checkout` (address confirmation + order review) -> "Place Order" -> `/payment` (mock payment form) -> `/payment_done/{orderId}` (order confirmation) -> "Download Invoice" (`/download_invoice/{orderId}`). Adding item(s) to cart itself is explicitly OUT OF SCOPE here and is reused as-is from the existing Products/Cart chunks (`ProductDetailsPage.addToCartAndViewCart()`, `CartPage`) — this plan does not re-test add-to-cart display/removal, which are already covered by `specs/cart.plan.md`. The already-implemented Cart-chunk scenario "Clicking Proceed to Checkout while not logged in shows the login/register modal" (`tests/cart/cart-checkout-gate.spec.ts`) is also reused/referenced, not re-verified in detail — this plan's login-gate scenario only re-triggers the modal as an entry point into its own distinct coverage (registering through the gate and successfully resuming checkout), matching published Test Case 14 ("Place Order: Register while Checkout").

This flow requires a logged-in account with at least one cart item, so every scenario below creates one disposable test-user account via the existing `SignupPage.generateTestUser()` / `SignupPage.registerAndLogin(loginPage, ...)` pattern (see `tests/pages/SignupPage.ts`), and deletes that account at the end via the standard `Delete Account` flow (same pattern as `tests/account/delete-account.spec.ts`) — CONFIRMED LIVE that account deletion works identically and without error even after a real order has been placed under that account (tested end-to-end: registered an account, added an item, completed a full order/payment, then deleted the account — got the standard "Account Deleted!" confirmation with no special-cased behavior). No scenario in this plan needs to leave an orphaned account or a stranded order.

PAYMENT-DATA SAFETY: every scenario that reaches the `/payment` form uses only obviously-fake, non-functional test data — Name on Card "Test User", Card Number "4242424242424242" (an obviously-fake, well-known dummy pattern, never a real card), CVC "123", Expiry "12"/"2030". No real or real-looking personal payment data is ever used.

**Page Object plan:** a NEW `tests/pages/CheckoutPage.ts`, extending `BasePage`, covering `/checkout`, `/payment`, and `/payment_done/{id}`. It composes rather than reimplements: `CartPage` (for `proceedToCheckoutButton`/`clickProceedToCheckout()`/`checkoutModalLoginLink`, reused as constructor/method params exactly like `SignupPage.registerAndLogin(loginPage, ...)` already does), `LoginPage` (for `startSignup()` when registering through the gate), and `SignupPage` (for `fillAccountInformation()`/`submit()`/`continueButton`/`registerAndLogin()` and the Delete Account pattern via `BasePage.deleteAccountNavLink` + `SignupPage.accountDeletedHeading`). `CheckoutPage` does NOT redeclare any of their locators.

`CheckoutPage.ts` locators (confirmed live): `addressDetailsHeading` (`getByRole('heading', {name: 'Address Details'})`), `deliveryAddress` (`#address_delivery`), `billingAddress` (`#address_invoice`) — both nested inside a `div.checkout-information` that carries the ONLY `data-qa` attribute found anywhere on `/checkout`: `data-qa="checkout-info"` (confirmed via a full-page `[data-qa]` DOM scan — no other element on this page, including the review table, comment box, or Place Order link, carries `data-qa`); `reviewOrderHeading` (`getByRole('heading', {name: 'Review Your Order'})`); `orderReviewTable` (`#cart_info table`, class `table table-condensed` — same row-markup convention as `CartPage`'s cart table: `.cart_description h4 a` name/link, `.cart_description p` category, `.cart_price p` unit price, `.cart_quantity button` quantity, `.cart_total p.cart_total_price`-style line total) plus a final non-product row containing an `h4` "Total Amount" heading and its value `p`; `totalAmountRow`/`totalAmountValue` (locate the row containing that "Total Amount" heading); `commentTextarea` (`textarea[name="message"]`, no id/data-qa); `placeOrderButton` (`a.check_out[href="/payment"]` — note this reuses the exact same `check_out` CSS class as `CartPage.proceedToCheckoutButton`, so it must be disambiguated by `href` and by only existing on `/checkout`, never both on the same page). Payment-page locators (confirmed live, `data-qa` present on EVERY field here — sharply different from `/checkout`, reconfirmed per-page rather than assumed): `paymentHeading` (`getByRole('heading', {name:'Payment'})`), `nameOnCardInput` (`[data-qa="name-on-card"]`), `cardNumberInput` (`[data-qa="card-number"]`), `cvcInput` (`[data-qa="cvc"]`), `expiryMonthInput` (`[data-qa="expiry-month"]`), `expiryYearInput` (`[data-qa="expiry-year"]`), `payButton` (`[data-qa="pay-button"]`) — all 5 inputs confirmed via DOM read to carry the native HTML `required` attribute with no `maxlength` restriction. Order-confirmation-page locators (`/payment_done/{id}`, also has `data-qa` present): `orderPlacedHeading` (`[data-qa="order-placed"]`, an `h2`, exact text "Order Placed!"), `orderConfirmationMessage` (exact text "Congratulations! Your order has been confirmed!" — NOTE this is the live-confirmed wording; it differs from published Test Case 14/24's doc text "Your order has been placed successfully!", and the live text is authoritative for all assertions in this plan), `downloadInvoiceLink` (`a[href^="/download_invoice"]`, no `data-qa`, class `btn btn-default check_out`), `continueButton` (`[data-qa="continue-button"]`).

`CheckoutPage.ts` methods: `proceedToCheckoutFromCart(cartPage)` (click `cartPage.proceedToCheckoutButton`, wait for `addressDetailsHeading` to become visible — for the already-logged-in path where clicking goes straight to `/checkout` with no modal); `registerViaCheckoutGate(cartPage, loginPage, signupPage, name, email, password, accountInfo?)` (composed helper for the register-while-checkout path: `cartPage.clickProceedToCheckout()` to open the modal, click `cartPage.checkoutModalLoginLink`, wait for `/login`, `loginPage.startSignup(name, email)`, `signupPage.fillAccountInformation({password, ...accountInfo})`, `signupPage.submit()`, `signupPage.continueButton.click()` — deliberately does NOT call `SignupPage.registerAndLogin()` as-is, since that helper starts with its own fresh `loginPage.gotoLogin()` navigation rather than arriving at `/login` via the modal's link); `getAddressText(section)` (returns the given address-section locator's normalized inner text, for comparing against the account's own registration fields); `fillComment(text)`; `clickPlaceOrder()` (click `placeOrderButton`, wait for `paymentHeading` to become visible); `fillPaymentDetails({nameOnCard, cardNumber, cvc, expiryMonth, expiryYear})`; `submitPayment()` (click `payButton` — callers that need to assert on the resulting network request/URL do so around this call); `getOrderIdFromUrl()` (parses the trailing integer from a `/payment_done/{id}` URL); `downloadInvoice()` (`Promise.all([page.waitForEvent('download'), downloadInvoiceLink.click()])`, returns the `Download` object for content/header assertions).

**Confirmed technical facts from live exploration (binding for this plan, not to be re-guessed by the generator):**
- `/checkout` IS a real server-rendered page load (confirmed via `browser_network_requests`: `GET /checkout` -> 200, a full navigation, not an XHR/client-side render) reached by clicking `a.check_out` on `/view_cart` while logged in — no modal appears in this case (contrast with the logged-out case, already covered by the Cart chunk, where the same click instead reveals `#checkoutModal` with zero network requests).
- `/checkout`'s address markup (confirmed with two different disposable accounts, each using distinct address data): `div.checkout-information[data-qa="checkout-info"]` wraps two `<ul>` blocks, `#address_delivery` ("Your delivery address") and `#address_invoice` ("Your billing address"), each rendering, in this exact order: title+first+last name (e.g. "Mr. Register Checkout"), the street address line, a combined "City State Zipcode" line (e.g. "Toronto Ontario M5H2N2"), the country name, and the phone number. Both `#address_delivery` and `#address_invoice` were confirmed to render byte-for-byte identical content to EACH OTHER, and both were confirmed to exactly match whatever values were submitted via `SignupPage.fillAccountInformation()` for that specific test's account — confirmed distinctly different between two accounts in the same exploration session (one used "United States"/"San Francisco"/"94107"; the other used "Canada"/"Toronto"/"M5H2N2"), proving this is genuinely per-account dynamic data, not a fixed/cached value (this is published Test Case 23's core assertion).
- The order review table (`#cart_info table`) uses the same per-row markup family as `/view_cart`'s cart table (product name+link, category, unit price, quantity-as-static-button, line total), plus one extra non-product summary row containing an `h4` "Total Amount" heading and a value `p` — confirmed with a single-item cart that this Total Amount equals the sole line total (Rs. 500 == Rs. 500); this plan does not exercise the multi-item summation case (already implicitly covered by the Cart chunk's per-row math, and out of scope here to avoid placing more than one real order).
- The comment textarea (`textarea[name="message"]`) and the "Place Order" link (`a.check_out[href="/payment"]`) carry NO `data-qa` attribute — confirmed via the same full-page `[data-qa]` scan that found only `checkout-info`.
- "Place Order" is a real navigation (`GET /payment` -> 200, confirmed via `browser_network_requests`), landing on a page whose Payment heading, all 5 input fields, and the Pay button ALL carry `data-qa` attributes (`name-on-card`, `card-number`, `cvc`, `expiry-month`, `expiry-year`, `pay-button`) — this is a sharp, page-specific contrast with `/checkout` having almost none, confirming `data-qa` presence must be checked per-page and never assumed carried over from a sibling step in the same flow.
- Submitting the payment form fires a REAL backend call: `POST /payment` -> 302, followed by `GET /payment_done/{orderId}` -> 200 (confirmed via `browser_network_requests`) — this is NOT a purely client-side mock (unlike the Cart chunk's login-gate modal, which fires zero network requests). However, no real third-party payment processor sits behind it — any syntactically-plausible card data was accepted with no server-side validation error path found during exploration. Per this project's stated scope (`specs/test-plan.md` §1: "payment gateway correctness" is out of scope), this plan asserts only on the resulting client-side flow and the real order record it produces (URL pattern, confirmation content, invoice download) — never on "the payment being genuinely processed/charged".
- The order id is a live, globally-incrementing integer assigned by the site (confirmed value `500` in this exploration session, guaranteed to differ on every future run) and appears in exactly two places that must always agree: the confirmation URL `/payment_done/{id}` and the Download Invoice link's `href="/download_invoice/{id}"`. No scenario in this plan hardcodes this id; it is always read dynamically from the URL after payment.
- "Download Invoice" triggers a real file download (confirmed via a captured Playwright `download` event, filename `invoice.txt`), backed by `GET /download_invoice/{id}` -> 200 with response headers `content-disposition: attachment; filename=invoice.txt` and `content-type: text/plain` (confirmed via `browser_network_request` header inspection) — clicking it causes NO page navigation (URL stays at `/payment_done/{id}` throughout). The downloaded file's exact text content, confirmed live for a Rs. 500 order under account first/last name "Checkout"/"Tester", was: `Hi Checkout Tester, Your total purchase amount is 500. Thank you` — i.e. the exact literal template is `Hi {FirstName} {LastName}, Your total purchase amount is {total}. Thank you`, where `{total}` is the numeric total with no "Rs." prefix and no decimal point.
- Register-while-checkout continuity (Test Case 14) confirmed live end-to-end: an item added to the cart while fully anonymous survives the entire "click `#checkoutModal`'s Register/Login link -> land on `/login` -> fill New User Signup mini-form -> fill Account Information -> Account Created -> click Continue -> land on `/` logged in" sequence — re-visiting `/view_cart` afterward showed the exact same line item untouched, and clicking "Proceed To Checkout" again from that point correctly proceeded straight to `/checkout` (no modal) with that same logged-in account's own address data.
- An incidental, NOT-asserted observation: after this session's full order was placed and the account later logged out/deleted, a subsequent `/view_cart` visit showed an empty cart. This plan does not isolate whether order placement itself clears the cart or whether logout/account-deletion does — it is noted here only so the generator does not mistake it for an untested defect; no scenario below depends on or asserts cart state after order placement.
- `/payment` was also confirmed reachable by direct URL navigation while fully logged out with an empty cart (no redirect/guard triggered) — this plan does not add a scenario for that edge case (low value, not part of the normal user flow), but it is noted so no scenario assumes a login/non-empty-cart guard exists at the `/payment` URL level itself; the actual gate the site enforces is the earlier `#checkoutModal` step on `/view_cart`, already covered by the Cart chunk.
- No seed/reset API exists for this chunk (matches every prior chunk); every scenario below generates a unique disposable account via `SignupPage.generateTestUser()` and deletes it at the end via the standard Delete Account flow, confirmed to work identically whether or not a real order was placed under that account.

**Priority legend:** P0 = Critical, P1 = High, P2 = Medium, P3 = Low. The full happy-path order placement (Scenario 1) is P0 — it is the core business transaction of the entire site and the highest-impact failure in this chunk. The login-gate-to-registration continuity (Scenario 2) is also P0 — a broken resume-after-registration would silently strand every brand-new customer at the single most common real-world entry point into checkout (an anonymous shopper who has never registered), and it is the one flow explicitly named by two published test cases (TC14, TC23). The native payment-field validation check (Scenario 3) is P2: it is boundary/negative coverage of browser-native HTML5 behavior rather than custom application logic, included for equivalence-partitioning completeness (empty vs. partially-filled vs. fully-filled required-field classes) but carrying materially lower risk than the two P0 transactional paths.

#### 1.1. Full checkout happy path: existing logged-in session through order placement and invoice download

**File:** `tests/checkout/checkout-happy-path.spec.ts`

**Steps:**
  1. Generate a disposable test user via SignupPage.generateTestUser() and register+log in via SignupPage.registerAndLogin(loginPage, name, email, password) (default account-information values: title 'Mr.', DOB 10 May 1990, first/last name 'Test'/'User', address '123 Test Street', country 'United States', state 'California', city 'San Francisco', zipcode '94107', mobile '1234567890'). Then add product 1 ('Blue Top', confirmed unit price 'Rs. 500') to the cart via ProductDetailsPage.addToCartAndViewCart(1) and land on /view_cart.
    - expect: The header shows text containing 'Logged in as {name}' for this disposable account.
    - expect: '#cart_info_table' contains exactly 1 row for product 1 showing unit price 'Rs. 500', quantity '1', and line total 'Rs. 500'.
  2. Click 'Proceed To Checkout' (a.check_out) from /view_cart.
    - expect: The resulting page URL equals exactly '/checkout' (a real server-rendered navigation, confirmed via network inspection) — '#checkoutModal' does not appear at all, since the user is already logged in.
    - expect: An 'Address Details' heading (h2) is visible.
    - expect: Both '#address_delivery' and '#address_invoice' are visible and each shows, in order: 'Mr. Test User', '123 Test Street', 'San Francisco California 94107', 'United States', and '1234567890' — the exact same values passed into fillAccountInformation for this test's disposable account, confirming both delivery and billing blocks reflect this account's own registration data.
    - expect: A 'Review Your Order' heading (h2) is visible, and the order review table ('#cart_info table') contains exactly 1 product row for 'Blue Top' showing unit price 'Rs. 500', quantity '1', and line total 'Rs. 500', followed by a 'Total Amount' row showing 'Rs. 500' — equal to the single line total since there is only one item in the cart.
  3. Type a short comment (e.g. 'Please deliver in the morning.') into the comment textarea ('textarea[name="message"]'), then click 'Place Order' ('a.check_out[href="/payment"]').
    - expect: The resulting page URL equals exactly '/payment'.
    - expect: A 'Payment' heading (h2) is visible, and all 5 payment fields ('[data-qa="name-on-card"]', '[data-qa="card-number"]', '[data-qa="cvc"]', '[data-qa="expiry-month"]', '[data-qa="expiry-year"]') plus the 'Pay and Confirm Order' button ('[data-qa="pay-button"]') are visible via their data-qa locators.
  4. Fill the payment form with only obviously-fake test data — Name on Card: 'Test User', Card Number: '4242424242424242', CVC: '123', Expiration Month: '12', Expiration Year: '2030' — then click 'Pay and Confirm Order'.
    - expect: A network request 'POST /payment' is observed returning an HTTP 302 response, confirming order placement here IS backed by a real server-side call that creates an order record — unlike the Cart chunk's purely client-side login-gate modal — even though no real payment processor exists behind it; per project scope, only this client-side/order-record flow is asserted, never 'payment gateway correctness'.
    - expect: The resulting page URL matches the pattern '/payment_done/{n}' where {n} is a positive integer (the newly created order's id) — capture this id for use in the next step, never hardcode it.
    - expect: A heading with the exact text 'Order Placed!' ('[data-qa="order-placed"]') is visible.
    - expect: A paragraph with the exact text 'Congratulations! Your order has been confirmed!' is visible (this is the live-confirmed wording, which differs from the published Test Case 14/24 doc text 'Your order has been placed successfully!' — the live text is authoritative).
  5. Click 'Download Invoice'.
    - expect: A real file download is triggered (a Playwright 'download' event fires) rather than any in-page state change.
    - expect: The download is served by a network request 'GET /download_invoice/{n}' (the same order id captured in the previous step) returning HTTP 200 with a 'content-disposition' response header containing 'attachment; filename=invoice.txt'.
    - expect: The downloaded file's full text content equals exactly 'Hi Test User, Your total purchase amount is 500. Thank you' (first+last name = this disposable account's registered 'Test User', total = 500 matching the Rs. 500 order total) — a precise, previously-observed value, not a vague 'contains some text' check.
    - expect: The page URL remains unchanged at '/payment_done/{n}' after the click — no navigation occurs from downloading the invoice.
  6. Click 'Continue' ('[data-qa="continue-button"]'), then click the header 'Delete Account' link to remove this test's disposable account.
    - expect: 'Continue' navigates to '/'.
    - expect: The Delete Account flow shows the standard 'Account Deleted!' heading and 'Your account has been permanently deleted!' text (SignupPage.accountDeletedHeading), confirming account cleanup succeeds normally even though a real order was placed under this account earlier in the test.

#### 1.3. Payment form blocks submission until all required fields are filled (native HTML5 validation)

**File:** `tests/checkout/checkout-payment-validation.spec.ts`

**Steps:**
  1. Using a fresh disposable account (SignupPage.registerAndLogin) and 1 item added to cart (ProductDetailsPage.addToCartAndViewCart(1)), reach '/payment' via CartPage.proceedToCheckoutButton then CheckoutPage.clickPlaceOrder(). Read each of the 5 inputs' ('[data-qa="name-on-card"]', '[data-qa="card-number"]', '[data-qa="cvc"]', '[data-qa="expiry-month"]', '[data-qa="expiry-year"]') 'required' IDL property via locator.evaluate.
    - expect: The page URL equals '/payment' and a 'Payment' heading is visible.
    - expect: Each of the 5 inputs' '.required' DOM property equals true, establishing that native browser validation applies to every field before any submission is attempted.
  2. With every payment field left empty, begin listening for any 'POST' request to '/payment', then click 'Pay and Confirm Order' ('[data-qa="pay-button"]').
    - expect: No 'POST /payment' network request is observed — native browser validation blocks the form submission client-side before any network call is made.
    - expect: The page URL remains exactly '/payment' (no navigation occurred).
    - expect: The 'Name on Card' input's ValidityState reports 'valueMissing' equal to true (read via locator.evaluate(el => el.validity.valueMissing)), confirming the browser flagged it as the first invalid required field blocking submission.
  3. Fill only 'Name on Card' ('Test User') and 'Card Number' ('4242424242424242'), leaving CVC, Expiration Month, and Expiration Year empty, then click 'Pay and Confirm Order' again.
    - expect: Still no 'POST /payment' network request is observed.
    - expect: The page URL still remains exactly '/payment'.
    - expect: The 'CVC' input's ValidityState reports 'valueMissing' equal to true (the next empty required field in DOM order), confirming partial completion still does not satisfy native validation.
  4. Delete this scenario's disposable account via the header 'Delete Account' link. (The cart still holds its unpurchased item at this point, and no order was ever placed under this account.)
    - expect: The standard 'Account Deleted!' heading and confirmation text are shown, confirming cleanup succeeds even though this account still had a non-empty, unpurchased cart at the time of deletion.
